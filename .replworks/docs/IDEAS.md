# 한국형 Spark (가칭)

> 작성일: 2026-11-24
> 상태: **진행 중 — 직접 사용(dogfood) 단계.** 배포 형태는 미결정.
> 관련 레포: `cable8mm/laravel-portone`, `cable8mm/laravel-social-auth`

---

## 1. 한 줄 요약

해외에서는 Laravel Spark 같은 패키지로 "로그인 → 구독 결제 → 결제 포털"까지 한 번에 세팅하지만, 한국은 PG와 SNS 로그인이 달라 그대로 쓸 수 없다. 한국 환경(포트원 PG, 카카오·네이버 로그인)에 맞춘 **구독 SaaS 기반 계층**을 만들어 두루 쓸 수 있게 한다.

---

## 2. 문제

- Spark는 **Stripe와 Paddle만 지원**하며, 다른 결제사를 붙이도록 커스터마이징할 수 없다(공식 FAQ 기준). 한국 PG는 사용할 수 없다.
- 한국 PG는 빌링키를 발급해 두고 **서버가 매 결제 주기마다 직접 결제를 호출**하는 방식이라, 갱신 스케줄링·결제 실패 재시도·해지·중복 결제 방지를 앱이 직접 구현해야 한다.
- SNS 로그인도 카카오·네이버·애플 중심이라 해외 패키지가 기본 제공하지 않는다.
- 현재 이 공백은 외주(예: 크몽의 구독 웹서비스 구축 상품)로 메워지고 있다. 수요는 있으나 제품화된 해법이 보이지 않는다.

---

## 3. Spark가 하는 일 / 하지 않는 일 (비교 기준)

**하는 일 (현재 Spark)**

- 독립된 **고객용 결제 포털**: 플랜 선택·변경, 결제수단 수정, 인보이스 다운로드, 결제 내역, 구독 일시정지
- 월/연 플랜을 **설정 파일 하나로 정의** (체험 기간, 기능 목록 포함)
- 좌석(인원) 단위 과금, 정기 결제, 결제 실패 재시도, 인보이스 메일
- 결제사 **웹훅으로 구독 상태 동기화**
- 앱 코드와 분리되어 업그레이드가 쉬움
- 내부적으로 Laravel Cashier 위에 구현

**하지 않는 일**

- 로그인·회원가입, 팀 초대·권한 관리 화면 (다른 스타터킷의 영역. 팀 단위 청구는 팀 모델을 청구 대상으로 바꾸는 별도 설정 필요)
- Stripe/Paddle 외 결제사 지원

## 4. 현재 보유 자산

| Spark 쪽                                          | 보유 자산             | 상태                                       |
| ------------------------------------------------- | --------------------- | ------------------------------------------ |
| Cashier (결제·구독 로직)                          | `laravel-portone`     | v0.8.0 (2026-11 기준)                      |
| 소셜 로그인                                       | `laravel-social-auth` | Google·Kakao·Naver·Apple, Socialite 미사용 |
| **결제 포털 UI + 플랜 설정 파일 + 인보이스 화면** | —                     | **미완 (가장 큰 빈칸)**                    |

**`laravel-portone` 현재 기능 (릴리스 노트 기준)**

- PortOne V2 단건 결제: 준비 → 확정, 전액/부분 환불, 결제 내역
- 웹훅 기록 및 중복 처리 방지(exactly-once), 상태 변경마다 한 번만 발송되는 결제 이벤트
- 중복 결제 자동 취소, 영수증 URL 저장, 만료된 `PENDING` 정리(`portone:expire-pending`)
- 빌링키 발급·확인·삭제·결제
- **구독**: `Billable::subscribe()`, 스케줄 명령 `portone:charge-subscriptions`로 갱신, 거절 시 재시도(기본 1·3·5일), 해지 구독 종료, 활성 구독이 쓰는 빌링키 삭제 방지, 같은 기간 중복 결제 방지
- 빌링키 등록 화면: Blade 스텁, Inertia React 스텁 (v0.9.0 전까지 카드 결제만)

**확인이 필요한 항목** (릴리스 노트에서 확인되지 않음)

- 플랜 변경 및 일할 계산
- 현금영수증·세금계산서
- 팀·좌석 단위 과금
- 카드 외 결제수단(간편결제·계좌이체): v0.9.0 예정

## 5. 배포 형태 — 검토 중 (미결정)

배경: 한국에서 Laravel·Next.js 같은 특정 프레임워크 전용 오픈소스는 개발자 사용량이 낮아 국내 확산이 어렵다. `composer create-project` 형태만으로는 대상이 좁다.

| 안                                 | 내용                                                                                       | 장점                                             | 우려                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------ | ------------------------------------------------------------------------------ |
| A. 패키지 + 스타터킷               | 기존 Laravel 앱에 설치, 또는 `create-project`                                              | 이미 있는 자산 그대로 활용, 책임 범위 작음       | 한국 Laravel 사용층이 좁음                                                     |
| B. 호스팅 API + JS SDK (언어 무관) | Laravel 패키지를 엔진으로 두고 HTTP API·SDK 제공 ("한국판 Supabase Auth + Stripe Billing") | Next.js/Node 개발자·AI 코딩 사용자까지 대상 확대 | 빌링키·웹훅을 서비스가 쥐게 되어 보안·장애 책임이 커짐, PG 계약 구조 확인 필요 |
| C. 웹사이트 빌더형                 | 비개발자용 UI를 B 위에 얹음                                                                | 시장 확대                                        | 고객 확보가 핵심 과제가 됨, 빌더 UI 자체 개발 부담, AI 앱 빌더와 경쟁          |

현재 방향성(제안, 확정 아님): A로 직접 써 보며 검증 → 필요 시 B → 사용 양상을 본 뒤 C를 검토. Laravel 패키지는 어느 경우에도 엔진 겸 셀프호스팅 옵션(오픈소스)으로 유지.

## 6. Build Principles 점검

- **Buy before Build**: Spark는 한국 PG를 지원하지 않아 구매로 대체할 수 없다 → 통과
- **Integrate before Rebuild**: PG 추상화는 포트원이 이미 제공하므로 자체 추상화 계층은 만들지 않는다 → 포트원 단일 연동 유지
- **Build only after repeated pain**: 본인 서비스에서 반복해서 필요했던 결제·로그인 기반을 패키지화한 것 → 통과
- **Publish reusable infrastructure**: 패키지로 공개되어 있음 → 진행 중

**체인 조건**: (1) 다음 타깃 제품에 실제로 필요한가, (2) 같은 문제를 겪는 다른 개발자에게도 독립적으로 유용한가. 두 조건 충족 여부는 직접 사용 결과로 판단한다.

---

## 7. 리스크

- **책임**: 결제 코드는 버그가 곧 고객 손해. 이중 결제·웹훅 누락 방어, 보증 범위 명시, PG API 변경 대응이 지속적인 유지보수 부담.
- **호스팅 시 보안**: 암호화된 빌링키와 결제 웹훅을 서비스가 보관. 보안·감사 로그·장애 대응 체계 필요.
- **PG 계약 구조**: 각 사용자가 자기 명의로 포트원/PG와 계약하고 서비스는 연결만 하는 구조인지, 정산을 대행하는 구조인지에 따라 규제가 크게 다름.
- **심사 의존**: PG 가맹 심사, 카카오 비즈앱·네이버 로그인 검수는 사용자가 직접 거쳐야 하므로 "설치 즉시 동작" 경험이 어렵다. 문서와 체크리스트가 제품의 일부.
- **노출**: 두 레포 모두 스타(GitHub) 0개. 패키지만으로는 발견되기 어렵다.
- **경쟁/대체재**: 외주 개발, 해외 AI 앱 빌더(Stripe 기준). 한국 PG·SNS 로그인을 기본 제공하는 빌더는 조사 시점에 확인되지 않음.

## 8. 검증 계획

1. **직접 사용(dogfood)**: 본인 서비스에 `laravel-portone` + `laravel-social-auth`를 붙여 실제 구독 결제를 운영한다.
2. 사용하면서 **고객용 결제 포털 화면**(플랜 선택·결제수단 변경·영수증)이 얼마나 자연스럽게 나오는지를 기준으로 부족한 부분을 기록한다. Spark 데모 화면을 벤치마크로 삼는다.
3. 위 "확인이 필요한 항목"(플랜 변경, 세금계산서, 팀 과금)에서 실제로 막히는 지점을 파악한다.
4. 5분 안에 로그인 → 테스트 결제까지 되는 **동작 데모**를 만든다.
5. 결과를 보고 배포 형태(A/B/C)를 결정한다.

---

## 9. 정책 초안 (플랜 변경 — 제안, 확정 아님)

구현 복잡도를 줄이기 위한 한국 SaaS 흔한 기본값.

- **업그레이드**: 즉시 적용, 남은 기간 차액 결제
- **다운그레이드·해지**: 현재 결제 기간 종료 후 적용 (일할 환불 없음)
- 세금계산서·현금영수증은 후순위로 두되, 요청 접수 필드와 화면은 초기에 포함

---

## 10. 재검토 조건

- 직접 써 봐도 반복해서 막히는 지점이 없거나, 쓸 이유가 본인 서비스에도 없을 때
- 포털 UI 없이 패키지만으로 충분하다는 사용 사례가 반복될 때 (빌더·스타터킷 방향 축소)
- 결제 책임·PG 계약 구조 때문에 호스팅(B) 형태가 현실적으로 불가능하다고 판단될 때
- 노출 수단 없이 인프라만 계속 쌓이고 실제 사용자 반응 확인으로 이어지지 않을 때
